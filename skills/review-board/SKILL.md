# Review board

Arguments: `$ARGUMENTS`

One page per review: `reviews/<slug>.html` in the project, generated by filling the project's reusable `reviews/skeleton.html` with git data plus the curation in `reviews/<slug>.review.json`, then opened with Lavish.
The orchestrator owns scope, review, verification, curation and the feedback loop.
The build is deterministic; a model touches the skeleton only on `--restyle`.
Everything the reader sees that is not a diff is a claim you verified.

Read before acting: [references/curation.md](references/curation.md) (the content schema), [references/page-contract.md](references/page-contract.md) (the sidecar, the skeleton, what the page does), [references/train.md](references/train.md) (merges, verification, acting on answers).

## Hard lines

- Never merge into the integration branch, `staging` or `main`, by any means. The PR opens and stops.
- Push only on the reviewer's explicit decision from the page.
- Never touch another session's worktree or branch; verification runs in a scratch worktree.
- Every finding, verification row and summary is verified, verbatim where it came from a tool, never softened.
- Current Lavish guidance comes from the CLI at run time: `npx -y lavish-axi --help`, `design`, `playbook code|input|explanation`.

## Phase 0 - Scope

Parse the arguments:

| Arguments                       | mode               | depth                                   |
| ------------------------------- | ------------------ | --------------------------------------- |
| one PR number                   | `pr`               | light                                   |
| branch name or `a..b`           | `branch` / `range` | light                                   |
| nothing                         | `branch`           | light, current branch vs `origin/HEAD`  |
| several PR numbers or `--train` | `train`            | full                                    |
| `--full` / `--light`            | as above           | forces the depth                        |
| `--restyle`                     | any                | adds the skeleton restyle step (Phase 5) |

Preflight: `git fetch origin --quiet`; `gh auth status` when PRs are involved; `node --version` is 22 or newer.
Then make sure the project is initialised:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/init.mjs            # creates reviews/, copies skeleton.html, gitignores generated pages
```

It is idempotent; report what it did when it created or changed anything, because it edits the project's `.gitignore`.
A dirty working tree becomes its own `worktree` change set in `branch` and `train` mode, never silently dropped.

Write the sidecar `reviews/<slug>.review.json` (schema in page-contract.md) with `"sessionId": "${CLAUDE_SESSION_ID}"` (add `"transcript": "~/.claude/projects/<encoded session cwd>/${CLAUDE_SESSION_ID}.jsonl"` when this session did not start in the repo root), then mark the first phase:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/usage.mjs mark reviews/<slug>.review.json scope
```

Mark every later phase the same way (`train`, `review`, `verify`, `curate`, `build`, `loop`, `act`), and `end` before the report.
Slugs: `pr-<n>`, `<branch with / replaced by ->`, `range-<a>-<b>`, `train-<YYYY-MM-DD>`.
For a PR that is not checked out: `git fetch origin pull/<n>/head:refs/review-board/pr-<n>`; base is `git merge-base origin/<baseRefName> refs/review-board/pr-<n>`.

## Phase 1 - Train (train mode)

Follow train.md: order, stacked detection, dry-run merges, branch, `--no-ff` merges with the parseable subject.
Build and open the page after the first merge; rebuild after each one so the reviewer watches the train grow.

## Phase 2 - Review (full)

For each change set, invoke the `code-review` skill (bundled with Claude Code) with the PR number, branch or range as its argument.
Where it is not available (another agent, an older Claude Code), spawn one `general-purpose` agent per change set, foreground, with the brief in [references/review-brief.md](references/review-brief.md); never review a set in this context, it has already seen the curation.
Transcribe the surviving findings verbatim into the sidecar's `curation.sets.<id>.findings` with file, line, severity, verdict.
`CLEAN` sets get an empty `findings` array and keep their summary.

## Phase 3 - Verify (full)

Run the repo's gates in a scratch worktree of the reviewed head, per train.md.
Record each command and its exact result as a verification row; compare any failure against the base before calling it pre-existing.

## Phase 4 - Curate

Light: title and body from `gh pr view` as `title` and `summary`; tiers and risk flags from rules; no notes, findings, verification or decisions.
Full: a behaviour-level summary per set, every core file with a one-line note in reading order, supporting notes where they help, findings from Phase 2, verification from Phase 3, flow decisions (push and open the PR, config fixes the review surfaced).
Read the diffs yourself to pick core files; a summary of a file you did not open is a guess.

## Phase 5 - Build

```bash
node ${CLAUDE_SKILL_DIR}/scripts/build.mjs reviews/<slug>.review.json
```

Read its report: fix any diff failure or curated path missing from the change set in the sidecar, then rebuild, before opening.

`--restyle` only: spawn one `general-purpose` agent, `model: opus`, foreground, with the restyle brief in page-contract.md.
It edits the `:root` block and the Shiki pair in `reviews/skeleton.html` to match the project's design system, following Lavish's design priority fetched from the CLI, and never touches the data placeholder or the behaviour.
The default skeleton is VS Code Dark Modern and needs no restyle.

## Phase 6 - Open and loop

```bash
npx -y lavish-axi reviews/<slug>.html
npx -y lavish-axi poll reviews/<slug>.html
```

Poll in the foreground and read each delivery completely.
The page has no forms: the reviewer talks through Lavish annotations, and the only page-made prompts come from selecting code.
By content:

- `question` / `change-request` (from a code selection, with file, side and line range): answer from the quoted code, opening the file when needed, or make the change as its own commit on the reviewed branch with its proving test, rebuild, reply with the sha. Reply with `lavish-axi reply` (or `poll --agent-reply` when another wait follows).
- An annotation on a finding (its text carries the id, e.g. `11-F1`): a disposition. `fix`, `accept` or `defer` by the reviewer's words; anything else is a question about it. Phase 7.
- An annotation on a decision row or one of its options: the answer to that decision; the push decision runs the push and PR steps in train.md.
- Any other annotation: a question or change request by content, with the annotated element as its context.

A `browser_disconnected` result is reported, not acted on; never reopen uninvited.

## Phase 7 - Act

Per train.md: `fix` is one commit per finding with its test; `defer` opens a GitHub issue and links it; `accept` is noted.
Rebuild so fix commits show as a `fixes` set, rerun affected gates, update the rows, reply with a receipt that names every finding the reviewer addressed and its outcome, and lists the findings still open.

## Phase 8 - Report

```bash
node ${CLAUDE_SKILL_DIR}/scripts/usage.mjs mark reviews/<slug>.review.json end
node ${CLAUDE_SKILL_DIR}/scripts/usage.mjs report reviews/<slug>.review.json
node ${CLAUDE_SKILL_DIR}/scripts/build.mjs reviews/<slug>.review.json
```

The rebuild puts the usage line in the page footer.
Final chat message: the headline (what was reviewed, findings count and dispositions, verification verdict, whether a PR was opened and its link), the Lavish link, then the usage line as the script printed it.
Never make the reviewer open the page to learn what it concluded.
